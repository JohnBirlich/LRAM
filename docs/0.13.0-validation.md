# 0.13.0: проверка трекера и адаптивного CPU

## Автоматизация

- Windows CI: `cargo test --locked`, `cargo clippy --all-targets --locked -- -D warnings`.
- Frontend: `npm run build`, `npm run test:capacity`.
- Fake process/log-owner fixtures не вызывают Restart Manager и не заменяют проверку реальных Roblox-процессов.
- Ранее опубликованные установщики не пересобираются и не заменяются.

## Ручной сценарий на затронутом ПК

1. Экспортировать пользовательский performance-профиль. Применить ULTRA, проверить 3% / 90s по умолчанию, затем сохранить 1% / 60s и 2% / 75s, перезапустить LRAM и убедиться, что выбор сохраняется. Импорт/экспорт нового профиля должен сохранять политику.
2. Постепенно запустить десять аккаунтов в исходной игре; первые девять свернуть. Сравнить окна с Home, Play, Accounts и Monitor, отдельно записать PID десятого окна и ID экземпляра. Не считать «Playing» API доказательством владения процессом.
3. Во время загрузки, в том числе дольше 2 минут, в карточке должно быть Loading без фонового CPU-потолка. После подтверждённого входа — полный выбранный прогрев. Это не освобождает явно заданный ручной CPU-лимит.
4. По окончании прогрева свернуть окно. Применённый потолок должен быть ровно выбранным 1/2/3%, независимо от числа клиентов. Это потолок, не требование потреблять столько CPU; проверьте также Windows CPU и работу самой игры. Не обещается фиксированный RAM/CPU либо число клиентов.
5. Вывести окно на передний план: фоновые ограничения должны сняться; свернуть — вернуться, если прогрев закончен. Задать ручной CPU-лимит конкретному клиенту: он должен сохраняться при фокусе и прогреве. Проверить Full quality отдельно.
6. Сделать телепорт/повторный вход: снять фоновые ограничения, дождаться подтверждённого входа и нового полного прогрева. FPS, графика, размер/сворачивание, previews и память не должны меняться от фокуса/телепорта.
7. При повторении потери живого окна проверить Checking process и отсутствие второго запуска/автоперезапуска. При восстановлении без рестарта должны сохраняться ID экземпляра и реальное окно; допустим новый PID, только если подтверждено владение его tracker-matched логом. При неоднозначности не назначать произвольный аккаунт.
8. Нормально закрыть окно: после подтверждения завершения оно исчезает из активных; автоперезапуск подчиняется настройкам. Во время явного Close не должно происходить «воскрешения». Проверить также выход из LRAM/запуск LRAM с ещё живыми клиентами.
9. Сохранить только диагностические строки instance ID/PID/CPU mode/process check. Перед передачей полного журнала проверить его на cookie, токены, приватные ссылки и персональные пути. Новые переходы таких секретов не записывают; старые сторонние строки не считаются безопасными автоматически.

Исходная причина потери десятого клиента не доказана. Изменения закрывают обнаруженные слабые места жизненного цикла трекера; успешный CI сам по себе не подтверждает исправление конкретного случая, отсутствие обнаружений Defender либо стабильность всех игр при 1% CPU.
